# Two-machine test plan — Brotatogether 1.5.2 + the 8 Oct fixes

Machines: **A** = `Main Machine - Brotato` (this one), **B** = `Remote Machine - Brotato`.
Branch under test: `ru-bugs-2026-10-08` @ `129cbe2`, six fixes, none validated.
Bug letters are the ones from `BUGS-2026-10-08-RU.md`.

## Ground rules

1. **Same build on both machines, proven, before every run.** `C:\brotato\bt_deploy.ps1 which`
   prints `baseline` or `patched` from markers in the deployed files. Both machines say the same
   word, or the run is void. This is the one failure that produces a clean-looking result from
   stale code, so it gets checked rather than assumed.
2. **Baseline first, then patched.** Every item is run on `baseline` to confirm the symptom is
   real and reproducible here, then on `patched`. A fix that was never seen to fail anything
   proves nothing.
3. The mod version stays `1.5.2` in both builds, so the compat gate cannot tell them apart —
   it checks game version, DLC set and mod `id:version`. That is why rule 1 is manual.
4. One run, one log. `godot.log` is per launch and gets overwritten; the launch scripts
   redirect stdout to `C:\brotato\logs\bt_*.log`. Keep the pair from the run that crashed.
5. **A stays on one mod.** `_compat_mods_string()` (`steam_connection.gd:1061`) stamps *every*
   loaded mod as `id:version` and the client refuses on any difference. B's retail install loads
   `Pasha-Brotatogether` alone, so A's tree has `Pasha-AutoBattler` moved out to
   `C:\brotato_23429717\mods-held-out\`. A's boot log must read `DONE: Setup 1 mods`. Put it
   back when the testing is done — the bot work needs it. Matching stamp on both sides:
   `bt_game_version 1.1.15.4` / `bt_dlc abyssal_terrors` / `bt_mods Pasha-Brotatogether:1.5.2`.
6. **B's install is never modified.** It runs stock Workshop 1.5.2 throughout, which makes it the
   baseline in both arms; only A switches build. Five of the six fixes sit in code paths that run
   on whichever side A occupies, and the sixth runs on the host, so A takes the role that puts the
   patched code in the path. B's repo clone is off limits — it holds ~2,468 lines of uncommitted
   work, 193 of them in `coop_shop.gd`.

## Fixture

**A only.** A's tree runs under the GodotSteam **editor** binary, so `OS.is_debug_build()` is
true and **F2** opens the in-game debug menu. B's retail install is not a debug build and has no
debug menu — which is why A hosts: the host is authoritative for gear and the shop, so A can
fabricate the exact pair each row needs for *either* player. The debug menu grants gold, adds a
named weapon to a chosen player, and toggles *cursed weapons* for what it adds. That is the whole
fixture — no file edits, nothing to keep in sync, and it works at any shop.

To make a combinable pair: at a shop, F2 → add the same common (tier 1) weapon twice to one
player → close the menu → click that weapon in the gear row → **Combine**.

## Roles

Who hosts matters, because most of these symptoms are specific to one side. Two role phases:

| Phase | Host | Client | Covers |
|---|---|---|---|
| P1 | **A** | B | A crash — A hosts so its debug menu can fabricate each row's pair for both players, and the host-side null-guard fix is in the path |
| P2 | **A** | B | E lobby freeze, F pick reset, H ready-then-leave — all observed by whoever stays, i.e. the host |
| P3 | B | **A** | B free reroll, C item limits — client-side symptoms, where A's client-side fixes run |

P3 comes last because it is the one phase with no fixture: as the client A cannot fabricate gear,
so the two Coupons that C needs have to be bought with real gold over a wave or two.

## P1 — B joins A

### 1. A, the crash (critical)

Run every row on `baseline` first. Expect rows 1 and 2 to crash and the rest not to; if the
pattern differs from the reporter's, say so rather than forcing the match.

| # | Setup | Who combines | Reporter's result |
|---|---|---|---|
| 1 | Starting weapon + a bought copy of the same common | Host (A) | crash |
| 2 | Same, client combines | Client (B) | crash |
| 3 | Two commons both added in the shop, neither a starting weapon | Host (A) | *unknown — this is the discriminator* |
| 4 | Two commons, debug menu's *cursed weapons* on for one of them | Host (A) | no crash |
| 5 | Two uncommons (blue) | Host (A) | no crash |
| 6 | Buy a weapon while already at max weapons | Host (A) | no crash |
| 7 | Recycle a weapon | Host (A) | no crash |
| 8 | Row 1 again, keyboard only, mouse never touched in the shop | Host (A) | *unknown — discriminator* |

Row 2 matters on its own: the reporter saw the client crash about five seconds after the host, and
the client-side candidate (aliased `ItemService` resources) predicts a client-initiated combine
fails differently from a host-initiated one.

Rows 3 and 8 are the point of the exercise:

- **3 vs 1** separates "tier 1" from "starting weapon". The leading candidate is that a client's
  starting weapons are the `ItemService` resources themselves rather than duplicates
  (`weapon_selection.gd:171`), which would make row 1 crash and row 3 not.
- **8 vs 1** separates the focus/freed-node candidate, which only became reachable when 1.5.2
  added mouse support, from the rest.

After each crash, from both machines: the last 80 lines of `godot.log` and of the redirected
stdout log. A GDScript null dereference prints an error and keeps running, so whatever took the
process down will look like a stack overflow, a freed-object access, or a native fault — the
line number is what picks between the three candidates.

Then `patched` and re-run rows 1–3. Row 1 still crashing is a real outcome, not a failed test:
it rules the null-guard out and leaves the aliasing and focus candidates.

## P2 — B joins A (same roles as P1)

### 4. E, lobby freeze when the partner leaves

- `baseline`: B joins, both reach character selection, A picks a character but does **not** ready
  up, then B leaves the lobby (quit to menu). On A: does the character description blank out, and
  do the arrow keys stop moving the selection? The predicted mechanism is A's own panel being
  cleared and left with nothing holding focus.
- Also run the variant where A *has* readied up before B leaves — the re-apply path restores a
  slot that was selected, so that one is predicted to survive.
- No fix is written for this. The run is to confirm the mechanism before writing one.

### 5. F, your pick resets when someone joins

`baseline`: A picks a character, B joins. Expect A's pick to be dropped. Confirms the known
trade-off and tells us whether re-applying the pick after the reload is enough.

### 6. H, ready-then-leave

`baseline`: both in the shop, B presses Ready, then B quits to the main menu. A starts the wave.
Record: does the wave start, does a body for B spawn and die immediately, and are coins and XP
still halved? Then check whether A's Esc does anything (expected: nothing, by design).

### 7. G, new run after a network run

A, alone after P2: finish or quit a network run, then from the end screen press **New run**.
`baseline` expectation: the solo co-op role-join screen. `patched`: a normal solo character
select. This is the one item A can also check without B.

## P3 — A joins B (client-side fixes)

### 8. B, free reroll in the client's first 2-3 seconds

- `baseline` on A: A enters the shop and immediately, before items appear, presses reroll. Confirm
  it costs 0 and the shop rerolls. Note A's gold before and after.
- `patched` on A: same timing. Expected: reroll, buy, combine, discard and GO all do nothing until
  the first shop packet lands, then everything works normally. Watch for the opposite failure — a
  client stuck unable to press GO, which would be the gate never clearing.

### 9. C, item limits reading 0/x on the client

- `baseline` on A: get A two Coupons by buying them. A's panel should read `Limit 0/3`, a third
  Coupon in the shop should also read `0/3`, and it should stay `0/3` after buying. Check *Fairy*'s
  bracketed values are zeros on A and real on B's view of A.
- `patched` on A: the counts should match what B sees for A, checked across two consecutive shops —
  the bug is a stale cache, so one shop could be right by accident.

## Not covered

Three or more players. Two machines only exercise the 2-player path. We can confirm the lobby
advertises `(2/4)` and that slots 3 and 4 unlock, but not that a third player seats correctly.

## RESULTS — 2026-10-10

### Setup change: the second machine cannot play

`Remote Machine - Brotato` has no GUI control (terminal session, no computer-use tooling), so it
cannot operate a second seat. Its permission layer also refuses to kill the Godot process, so a
launch there is one-way. Its config was confirmed compatible before that came up and matches
exactly: `bt_game_version 1.1.15.4` / `bt_dlc abyssal_terrors` / `bt_mods Pasha-Brotatogether:1.5.2`
from stock Workshop 1.5.2. It has taken the static-analysis and log-forensics role instead.

Its clone holds ~2,468 uncommitted lines, 193 of them in `coop_shop.gd` — the same file as four of
these six fixes. Untouched, and flagged to the user.

### What replaced the two-machine plan

`--bt-solo` + `--bt-combine` on this machine alone. The mod's own solo-test path
(`ui/multiplayer_menu.gd:98`) fakes a lobby of one with `is_solo_test`, so `in_multiplayer_game` is
true and the co-op shop runs with the full **host** path live. The harness then fabricates a
combinable pair and presses Combine in-process, printing before each step so a hard exit leaves the
failing step as the log's last line.

Runs are on the **release export template** (`godotsteam.36.template.windows.64.exe`), not the
editor binary. B caught the reason: `RunData._update_item_caches` (`run_data.gd:1596`) opens with an
`assert`, which is live in a debug build and compiled out of release. The reporter is on retail, so
the editor binary could abort where they continue, and vice versa. The log confirms release
semantics: `Options override feature tag "editor". does not apply, skipping.`

### Host-side combine rows

All on the release template, solo (one player), two shops per run:

| Row | Build | Pair construction | Result |
|---|---|---|---|
| `common,alias` | baseline | same `ItemService` resource twice (a client's post-selection state) | **survived** |
| `common,mixed` | baseline | aliased starting weapon + `add_weapon` duplicate — the reporter's case | **survived** |
| `common,mixed,hidden` | baseline | as above, `MOUSE_MODE_HIDDEN` forced (candidate 3's condition) | **survived** |
| `common,mixed` | patched | regression check | **survived** |

In every row the combine produced the right tier-2 weapon and the forced post-combine
`send_shop_state` completed. No script errors beyond the two benign `pd_*` modloader ones.

### What this establishes

**The host-side combine does not crash on its own.** Not with an aliased pair, not with the
reporter's mixed pair, not with the focus-stale mouse mode, not on a release build. So the crash
needs the second player actually connected — which fits the reporter's account that the host dies
first and the link breaks. The untested surface is the part of `send_shop_state` that only runs with
`player_count == 2`: the other player's gear container, their synced stats, and
`_focus_dictionary_for_player(1)`.

It also establishes that the six fixes do not break the host combine path.

### Still blocked on

A second seat for the two rows that need one: the client-initiated combine, and a host combine with
a client connected. Either the user plays it, or the reporter sends `godot.log`.

### Candidate status after B's static pass

- **Candidate 2 (unguarded null)** — ruled out as the crash. A Godot 3 null dereference aborts the
  function and continues; it cannot exit the process. Still a real bug, and still fixed.
- **Candidate 3 (freed-node focus read)** — ruled out as the crash. Every use of `focused_control`
  in `_focus_dictionary_for_player` is an object *equality* test, which compares ObjectIDs and never
  dereferences. Comparing against a freed node is safe and simply never matches, so the failure mode
  is a wrong focus, not a fault. The `hidden` row above agrees.
- **Candidate 1 (aliasing)** — still the only candidate shaped like freeze-then-exit, and B found a
  second consequence worth more than the first: weapons pushed in by `_weapon_selection_completed`
  never had `apply_item_effects` run, yet combining them removes them through
  `after_weapon_removed` → `unapply_item_effects`, so every combine of a starting weapon drives that
  player's stats net-negative over state that was never applied. That is a real corruption bug on
  its own, and the `.duplicate()` fix cures it. But it did not crash here.
