## A′ / A″ — the crash, reset

Two things the second message establishes:

1. **It is not combine-specific.** The second crash followed a plain purchase. Our four findings —
   aliased starting weapons, the unapply-without-apply corruption, the identity divergence, the
   load-bearing `queue_free` — are all combine-path. None of them reach a purchase.
2. **The crashing side has flipped.** First report: host froze first, client followed ~5 s later.
   Second report: the client died and the host carried on alone. Left as **two possibilities, not a
   correction** — two distinct crashes is at least as likely as one account being wrong, and
   "client dies, host plays on" is a different failure from "host freezes, client follows".

The common shape across both of today's crashes is narrower and different from a combine: **a
client-initiated shop action whose target the two sides resolve differently.** Combine and buy both
send an id the host resolves in its own copy of that player's state.

The reporter's own hypothesis — that the host was watching their cursor on a grey weapon while they
combined a purple one — is the **index-based focus mirroring** divergence from bug D showing itself.
What the host *sees* of a client's selection is cosmetic. But it is direct evidence the two sides'
lists disagree, which is the precondition for an action naming something the other side resolves
differently.

### What was eliminated today

The most promising client-side candidate was traced end to end and does **not** crash:

`_shop_item_for_dictionary` and `_inventory_item_for_dictionary` could leave their result null and
then dereference it, aborting mid-rebuild. Right side (client), right trigger (a purchase the host
echoes back), right moment. But B's downstream trace and my own reading agree it is script-error
class throughout: the abort leaves a null entry, `set_shop_items` (`shop_items_container.gd:200`)
raises "Invalid get index '0' on base: 'null instance'" and aborts its loop, and `set_shop_item`
(`shop_item.gd:132`) would die on `p_item_data.value` before reaching anything native. The only
native-adjacent call on that path, `ImageTexture.create_from_image` at `:142`, is gated behind the
`hp_shop` effect.

So it errors and continues. **Still a real bug with visible consequences** — see J and L — but not
the process death.

### What to ask for now

The **client's** `godot.log`, not the host's. We have been asking for both; it is the client that
died in both of today's crashes, and that is a much sharper request than before.

## J — the client's inventory is genuinely wrong, in combat too

This is the most valuable item in the first message, and the reporter is right that it is not
cosmetic.

`_update_shop` pushed helper results straight into `RunData.players_data[player_index].items` and
`.weapons`. An id the client cannot resolve makes the helper return null, and **null went into
`RunData`** — not into a display list. So the client's inventory is wrong everywhere that reads
`RunData`, which includes combat. That is exactly what they describe, and it outranks the
focus-mirroring explanation for the visual errors.

B's observation that `_weapon_for_dictionary` was *already* guarded internally and its caller
*still* pushed null is the right diagnosis of where the defect lives: **at the push, not in the
helper.**

**Fixed** on `ru-bugs-2026-10-08`: all three push sites now drop unresolvable entries and log them,
and the helpers return a clean null/`[]` rather than dereferencing. Note the push-site guards for
weapons and items landed in the first batch (`129cbe2`); the shop-items one and the helper returns
landed in `43c543a`.

## K — cursed items on the client

Confirmed literal, not visual. `curse_item` (`dlcs/dlc_1/dlc_1_data.gd:49`) does far more than set a
flag: it boosts the stats via `_boost_weapon_stats_damage` at `:61` and rebuilds the effects array at
`:63-70`, returning a **new** resource. The wire carried only a `CURSED` boolean, so the client set
that flag on a plain `duplicate()` — cursed marker, uncursed numbers. The two sides then hold
different values for the same item.

Worse, and B's catch: `curse_item` returns early on an already-cursed item (`:50`), so the flag-only
state was **sticky** — once set, no later `curse_item` call could ever repair it.

**Fixed** in `43c543a`: the host sends the factor it rolled and the client rebuilds through
`curse_item` with randomisation off. That is deterministic —
`_get_cursed_item_effect_modifier` (`:356`) zeroes both random sources under that flag, leaving
`max(min_modifier, fixed_base)`.

**Residual, flagged:** the host rolls a factor *per effect* and we send only the maximum, so an item
whose effects got different factors is rebuilt with all of them at the maximum. Single-effect and
uniform-factor items are exact. Closing the gap means sending the resulting stats and effects
outright — a much larger wire change than a display discrepancy justifies while the host already
ships authoritative per-player `STATS`.

**Audited, so that "display only" is a claim and not an assumption** (B asked for this, correctly —
the argument only holds while nothing client-side *computes* from the reconstructed item objects):

- The client takes aggregate effects **off the wire** — `coop_shop.gd:433`,
  `player_data.effects = player_data._deserialize_effects(...)` — and never re-derives them from its
  item objects. `apply_item_effects`, `unapply_item_effects` and `update_item_related_effects` appear
  nowhere in the mod's client-side code.
- The only `.stats` reads in the mod are enemy and turret stats for spawn replication
  (`extensions/main.gd:703, 738, 741, 865, 1588`), not item stats.
- `curse_item` does **not** touch an item's `value`, so the shop price the client computes locally in
  `set_shop_item` is correct for a cursed item regardless of the factor.

So the inaccuracy cannot propagate into player state or prices. It is confined to what a tooltip
shows.

**Known issue, and not filed as cosmetic.** B's other point is worth keeping even though the audit
came back clean: a player makes buying decisions from an item tooltip. A cursed item showing the
wrong numbers on the client is bad information at the moment of a decision, not a rendering
artefact. Biased high is the kinder direction to be wrong in. It belongs in the release notes as a
known limitation for multi-effect cursed items rather than being treated as closed.

## L — the shop panel keeps the previous shop's items

Fallout from the same null: when `set_shop_items` aborts mid-loop, the slots it had not reached yet
never get `set_shop_item` *or* `deactivate()`, so they keep rendering the previous shop's contents.
A visible desync, and a candidate for some of the stale-item sightings. Fixed by the J guards.

---

## M — item duplication via lock → failed reroll

Not fixed. The strongest lead is B's: `_update_shop` expands items with
`for _i in item["NUMBER"]`, so a stale or wrong `NUMBER` duplicates entries on every apply — the
right shape for "locked it, rerolled, nothing happened, next shop had two". Worth checking against
`RunData.locked_shop_items` and the host's `lock_player_shop_item`, since the client never writes
that array itself.

Needs the screenshot they mention (not attached) and ideally the sequence repeated once.

---

## N, O, P, Q — the smaller ones

- **N**, the client not seeing the reroll price, is almost certainly the unset `_reroll_price` behind
  bug B, which is already gated. Needs confirming that the *price label* updates and not just the
  button's affordability tint.
- **O**, no ban function for the client, is a design decision: either mirror the host's ban control
  to clients, or tell players it is host-only. The reporter's instinct that it is illogical is fair.
- **P**, the weapon description scrollbar, is uninvestigated.
- **Q**, the selection cursor jumping, the reporter themselves attributes to vanilla, and they may be
  right. It is also exactly where the mod's focus mirroring lives, so it should not be taken on trust
  either way.

## 3. Fixes in this batch

Commit `43c543a` on `ru-bugs-2026-10-08`, client-side, one additive wire field:

| Fix | Bugs | Wire |
|---|---|---|
| Drop unresolvable ids at all three push sites; helpers return clean | J, L | no change |
| Send `CURSE_FACTOR`; client rebuilds via `curse_item` with randomisation off | K | additive, `.has()`-guarded |

The curse factor is the first wire addition in this work. It is backward compatible in one
direction: a patched client against an unpatched host falls back to flag-only. An unpatched client
against a patched host simply ignores the field.
