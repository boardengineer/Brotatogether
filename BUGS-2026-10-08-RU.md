## A. The combine crash (critical)

### What the code does
Host path, `extensions/ui/menus/shop/coop_shop.gd:243`:

```gdscript
func _on_item_combine_button_pressed(weapon_data: WeaponData, player_index: int) -> void:
    if in_multiplayer_game:
        if steam_connection.is_host():
            pending_force_focus.push_back(player_index)
            ._on_item_combine_button_pressed(weapon_data, player_index)   # vanilla combine
        steam_connection.shop_combine_weapon(_string_for_weapon(weapon_data), false, player_index)
```

Client path, `coop_shop.gd:253`:

```gdscript
func _client_shop_combine_weapon(weapon_string : String, _is_upgrade: bool, player_index : int) -> void:
    _on_item_combine_button_pressed(_weapon_for_string(weapon_string, player_index), player_index)
```

No echo loop: the host's `shop_combine_weapon` only calls `request_shop_update()`
(`steam_connection.gd:1993`), so the two sides do not ping-pong.

### Candidate causes, ranked

**A1 — unguarded null weapon (`coop_shop.gd:636`).**
`_weapon_for_string` matches **only on `my_id`** over the gear container's children and returns
`null` when nothing matches:

```gdscript
func _weapon_for_string(weapon_string : String, player_index : int) -> WeaponData:
    for element in _get_gear_container(player_index).weapons_container._elements.get_children():
        if _string_for_weapon(element.item) == weapon_string:
            return element.item
    return null
```

Note the asymmetry inside the same file: `_client_shop_lock_item:258` and
`_client_shop_unlock_item:267` **do** check for `null` (with a comment explaining that an
unresolvable name is normal), while the combine and discard handlers (`:253`, `:168`) do not.
A `null` here reaches vanilla `_combine_weapon` (`ui/menus/shop/base_shop.gd:636`), which
immediately does `weapons_container._elements.remove_element(weapon_data, 1, true)` and then
`weapon_data.upgrades_into` on the null. Cheap to fix regardless of whether it is *the* crash.

**A2 — host and client weapon lists are not the same objects (`extensions/ui/menus/run/weapon_selection.gd:171`).**

```gdscript
func _weapon_selection_completed(selected_weapons : Array) -> void:
    for player_index in RunData.get_player_count():
        RunData.players_data[player_index].weapons.clear()
        for weapon_index in selected_weapons[player_index].size():
            RunData.players_data[player_index].weapons.push_back(selections_by_string_key[...])
```

`selections_by_string_key` holds **the global `ItemService.weapons` resource instances**
(`weapon_selection.gd:25-26`), not duplicates. So on the client every starting weapon in
`players_data[i].weapons` *is* the shared item-database object — shared between players and with
the shop pool, and mutated in place by anything that writes `tracked_value`,
`dmg_dealt_last_wave` or `is_cursed`. Everywhere else the game goes through `RunData.add_weapon`,
which duplicates (`singletons/run_data.gd:983`).

This matters for the crash because **starting weapons are exactly the tier-1 weapons**, which is
the reporter's discriminator, and because vanilla `RunData.remove_weapon` (`run_data.gd:1067`)
erases by `ItemService.is_same_weapon` — a stats/effects comparison, *not* `my_id`. Two identical
non-cursed greys compare equal; a cursed and a non-cursed grey do not. That is the other half of
their discriminator: **the cursed combinations they tested are precisely the ones where the two
weapon objects are distinguishable.**

**A3 — focus is read after the combine freed the nodes (`coop_shop.gd:665`).**
`_combine_weapon` removes two inventory elements and adds one, then re-focuses *only* when the
mouse is hidden. `send_shop_state` -> `_focus_dictionary_for_player` then compares
`Utils.get_focus_emulator(player_index).focused_control` against the surviving children. In a
release template, touching a freed `Object` is not a caught script error. 1.5.2 is the release that
added mouse support (`f0092e2`, `b437f99`), which is also when `Input.get_mouse_mode()` stops being
`MOUSE_MODE_HIDDEN` and the re-focus at the end of `_combine_weapon` stops running — exactly the
condition that leaves a stale focused control behind. This fits "newest version", and it fits
"freezes, then crashes" better than a null dereference does: a GDScript null deref prints an error
and aborts the function, it does not take the process down.

### Why "tier 1 only" and "cursed is fine" are probably real but confounded
There is no tier-dependent branch anywhere in the mod (`grep -rn tier` over `Pasha-Brotatogether/`
hits only `client_main.gd` and the legacy `game_controller.gd`), and vanilla's only tier-0 special
cases are cosmetic (`item_service.gd:965-967`, `weapon.gd:110`). So the discriminator is almost
certainly *data*, not a tier test: tier-1 = starting weapons = the shared-instance case in A2, and
cursed = the case where the two objects differ. Their experiment is good evidence, just not direct
evidence of a tier check.

### What settles it
Their `godot.log` names the file and line. Path: `%APPDATA%\Brotato\logs\godot.log`; previous runs
are kept beside it as `godot_<date>_<time>.log`. Both machines, from the run that crashed.

## B. Client's shop is empty for 2-3 s, reroll costs 0

`coop_shop.gd:66` sets `waiting_to_start_shop = true` on the client, and the flag is only cleared
at the very end of `_update_shop` (`coop_shop.gd:484`). Until the host's first shop packet lands,
the client's panels are genuinely empty and `_reroll_price[player_index]` is still its default —
hence a free reroll. Pressing up/down makes the items appear because the focus change triggers a
state exchange.

**Fix:** while `waiting_to_start_shop` is true on a client, block shop input — return early from
`_on_RerollButton_pressed` (`:746`), `_on_GoButton_pressed` (`:177`) and the item/weapon button
handlers, and ideally dim the panel. The flag already exists; it just is not consulted.

A second, independent hardening: `_on_RerollButton_pressed` should not trust a locally-zero price.
The host re-sends `REROLL_PRICE` in every packet (`:347`), so a client with no packet yet should
treat the price as unknown rather than free.

## C. Client sees `Limit 0/3`, Fairy zeros

Two bugs stacked, both in `_update_shop`:

1. **Stale caches.** `RunData.get_nb_item` reads `items_nb_cache` (`run_data.gd:1537-1546`); there
   are also `different_items_nb_cache` and `duplicate_items_cache` (`run_data.gd:149-151`). Vanilla
   invalidates them through `_update_item_caches` on every add/remove (`run_data.gd:921, 945, 988,
   1080`). The client's `_update_shop` rewrites `players_data[i].items` wholesale
   (`coop_shop.gd:416-420`) and **never touches the caches**, so every count the shop asks for is
   whatever was cached when the client had nothing — zero. That is precisely "the shop pretends the
   second player has no items"; the reporter's own diagnosis is correct.
2. **Wrong order of operations.** `set_shop_items` (`:407`) runs *before* the items array is
   rebuilt (`:416`), so the limit labels are computed against the previous wave's inventory even
   once the caches are fixed.

**Fix:** in `_update_shop`, rebuild `weapons` and `items` first, then clear
`RunData.items_nb_cache[player_index]` and `RunData.different_items_nb_cache[player_index]` and set
`RunData.duplicate_items_cache[player_index] = null` (or call the existing
`RunData.reset_run_caches()` at `run_data.gd:599` if clearing all four slots is acceptable), and
only then call `set_shop_items`. The host's `0/3`-with-2-owned sighting is the same cache read on a
*remote* player's panel, so one fix covers both sides.

## D. Reversed item order, wrong description, "two separate bags"

Three pieces, one root:

- `extensions/ui/menus/shop/player_gear_container.gd:17` passes **`reverse = false`** where vanilla
  passes `true` (`ui/menus/shop/player_gear_container.gd:23`):
  `items_container.set_data("ITEMS", Category.ITEM, items, false, true)`.
  The override is compensating for the fact that the wire array is already in the host's *display*
  order, not data order (`coop_shop.gd:317-321` serialises `_elements.get_children()`).
- Vanilla stacking has a falsy-index bug: `ui/menus/shop/inventory.gd:103`,
  `var index = element_index.get(...)` followed by `if index:` — **index 0 is falsy**, so a second
  copy of whichever item type is *first in the array* never stacks and gets its own element. The two
  sides pass differently-ordered arrays, so this bites on one side only: **"two separate bags."**
- Focus mirroring is **index-based** (`coop_shop.gd:510-555`; `_focus_dictionary_for_player:665`
  sends `{"TYPE":"ITEM","INDEX":i}`). With the two sides' children in different order and with
  different stacking, index *i* means a different item on each side, so the host shows **the
  description of a different item**.

**Fix (removes all three):** send `RunData.players_data[i].items` in **data** order — one entry per
item, ids plus the cursed flag, no `NUMBER` collapsing — have the client rebuild the array in that
same order, then delete the `set_items_data` override so both sides run **identical vanilla display
code on identical input**. Order, stacking and index->item mapping then agree by construction.
Fixing the vanilla `if index:` bug in the extension is worth doing too, but it is cosmetic once the
arrays match.

## E / F. Lobby hangs on leave; your pick resets when someone joins

`extensions/ui/menus/run/character_selection.gd:50-51`:

```gdscript
# A join still reloads the scene (the simplest way to grow the vanilla panel set); a leave
# is handled in place so the remaining players keep their picks.
steam_connection.connect("lobby_players_updated", self, "reload_scene")
steam_connection.connect("lobby_roster_changed", self, "_on_lobby_roster_changed")
```

- **F** is that first line, exactly as the reporter describes it: a join reloads the character
  screen, so your selection is lost. A known trade-off, documented in the comment. A real fix is
  work (add the new panel without reloading); the cheap version — re-apply the local pick after the
  reload — is enough to kill the complaint.
- **E**: character selection *does* handle leaves, in `_on_lobby_roster_changed`
  (`character_selection.gd:479`) — it shifts `_player_characters` / `_has_player_selected` down,
  removes the vanilla panel, and then re-applies every surviving slot. The freeze is in that
  re-apply: it calls `_player_focused_character(i, character_item_to_string(_player_characters[i]))`
  for **every** index including the local player's, and for a slot that has not picked yet the
  string is `"RANDOM"` (`character_item_to_string:209`). `"RANDOM"` is not a key in
  `selections_by_string_key`, so in `_player_focused_character:215` both `selected_item` and
  `focused_element` stay null — `_clear_selected_element(player_index)` still runs, and the panel
  is then **never repopulated** because the repopulate is guarded by `if selected_item != null`.
  For the local player the refocus branch is skipped as well (`player_index != get_my_index()`), so
  nothing holds focus any more: **blank description and dead arrow keys**, exactly as reported. It
  recovers when the partner rejoins because a join runs `reload_scene` and rebuilds the screen from
  scratch — which is also why only *leaving* shows it.
  Fix: in `_on_lobby_roster_changed`, leave the local player's own slot alone (they did not leave),
  and in `_player_focused_character` treat an unresolvable id as "clear the panel and keep focus"
  rather than falling through with a half-cleared slot. Not implemented yet — I cannot repro a
  two-machine leave from here, and this one deserves a test rather than a blind patch.

## G. "New run" after death -> solo role selection

`brotatogether_options.in_multiplayer_game` is set true at
`extensions/ui/menus/run/difficulty_selection/difficulty_selection.gd:21` and is **never set back
to false anywhere in the mod** — `main_menu.gd:27` resets only `joining_multiplayer_lobby`.

(Vanilla itself is fine here: every exit from a run — New run, Restart, Exit, and the in-game
restart menu — goes through `RunData.reset()`, which already does `set_player_count(1, true)` and
`set_coop_run(false)` for a non-restart reset, `singletons/run_data.gd:493-496`. So `is_coop_run`
is *not* the stale flag.) What stays stale is the mod's own flag, and every extension in the mod
branches on it: `main.gd`, `unit.gd`, `item.gd`, `coop_shop.gd`, the shop containers and the
selection screens all keep taking their multiplayer path through the next **solo** run, including
`character_selection`'s co-op controls — which is how "new run" lands on the role-join screen.

**Fix:** clear `in_multiplayer_game` (and leave the Steam game lobby) from `RunData.reset()`, which
is the single choke point every exit path already passes through.

## H. Pause, and the ready-then-leave case

- **Esc does nothing** is deliberate: `extensions/main.gd:2006`

  ```gdscript
  func _check_for_pause() -> void:
      if not in_multiplayer_game:
          ._check_for_pause()
  ```

  Pausing is not synced, so the whole check is stubbed out — which also means there is no way back
  to the menu mid-run, hence Task Manager. **Fix:** a local-only menu that does *not* pause the
  scene tree (vanilla `pause()` does), offering "leave run" and settings. Needs a product decision:
  a true synced pause (host pauses everyone) is the nicer answer and more work.
- **Partner readies, exits to menu, host starts the wave -> partner dies instantly, rewards still
  split.** The leaver's slot is kept and flagged (`steam_connection.gd:290`, `left_players`),
  deliberately, so indices stay stable. `coop_shop.gd:756` already handles the GO quorum for a
  leaver, but the departed slot still counts as a player for reward splitting (the round-robin gold
  split, and xp). **Fix:** filter `left_players` out of the reward split and out of the wave-start
  spawn, rather than spawning a body that dies immediately.

## I. "More than 2 players"

1.5.2 **does** support up to 4: `locked_slots` is a 4-slot array (`steam_connection.gd:147`), the
character screen builds four player panels and slot controls, and the shipped change notes advertise
"Lock slots" and a lobby list showing e.g. `(2/4)`. So either they are on an older Workshop build,
or the host had slots locked, or something genuinely fails for them at 3+. Needs a question back,
not a fix yet.
